Added explanation (not part of the raw command output above) - how each
"triggered" value was actually decided. Straight from monitoring/monitor.py:
each check computes one number, then compares it against a fixed threshold.

| Check                 | Rule (exact code)      | Plugged in                | Result |
|------------------------|-------------------------|----------------------------|--------|
| confidence_drift       | z_score > 1.0           | 0.4183 > 1.0               | False  |
| oov_drift               | delta >= 0.05           | 0.0487 >= 0.05             | False  |
| output_balance_drift   | abs(delta) >= 0.10      | abs(-0.1597) >= 0.10       | True   |
| performance_drop       | drop >= 0.05            | 0.1318 >= 0.05             | True   |

Note: oov_drift and performance_drop are one-directional - "delta" and
"drop" are NOT wrapped in abs(), so they only fire if the number moved the
"bad" way (vocabulary rate going up, or macro-F1 going down). Only
output_balance_drift uses abs(), so it fires whether the POSITIVE share
swings up or down by 10+ points - there's no inherently "good" direction
for the output mix to move, so either direction counts as suspicious.

The NUMERIC SIGNAL DRIFT REPORT above (confidence, token_count,
oov_token_count) is descriptive only - a per-signal z-score shown for
context, not itself one of the four triggers. It uses the same >1.0
sigma cutoff as confidence_drift, which is why confidence appears in both
sections with the same shift value.

These are called "signals," not "features," deliberately: none of them
are columns in feature_store/feature_store.db. That table's real numeric
feature columns (Reviewer_Score, the two Review_Total_*_Word_Counts
columns) can't be used here - a live /predict request only ever sends raw
text, never the pre-split review halves or score those columns depend on,
so there's no live value to compare against a baseline for them. Token
count and OOV count stand in instead, since they're the only numeric
quantities computable identically from both the baseline text and a live
request's text.

Full explanation of what each signal means and why its threshold is set
where it is: docs/monitoring.md.
